## ISSUE 1 — App crashes on first launch ("app turned off"), works second launch

### Root causes (most → least likely)

1. **No React error boundary at the root of the tree.** Any unhandled JS
   error during initial render kills the WebView page. Android Capacitor
   surfaces a dead WebView as a process crash → "app turned off". Second
   launch works because the JS bundle is in cache and re-init runs from a
   warmer state, skipping the heavy first-touch path.
2. **Cold-start race between Auth0 + Mapbox + push notification init.**
   Three plugins fire within the first 500 ms; on slow Android devices
   main-thread starvation triggers ANR (Application Not Responding) if a
   frame can't draw within 5 s on cold start.
3. **AGP 8.2.1 + compileSdk 35 mismatch.** Build warned: "tested up to
   compileSdk = 34. You are strongly encouraged to update your project
   to use a newer Android Gradle plugin." Some resource resolution bugs
   in this combo throw at initial layout.

### Fixes shipped

- **`web/src/components/RootErrorBoundary.tsx` (NEW)** — wraps the entire
  React tree. Catches render errors, shows fallback UI with Reload button,
  pushes the trace to `window.__brooksErrors` for adb-debug capture, AND
  guards against infinite reload loops via sessionStorage counter (after
  2 reloads, switches to "uninstall + reinstall" advice).
- **`web/src/app/layout.tsx`** — wires the boundary as the outermost
  client component, around ThemeProvider + AppShell.
- **versionCode bumped 4 → 5** so install replaces any partial old state
  on the device.

### Verify after rebuild

If the app still "turns off" on first launch, this means the crash
happens BEFORE React mounts (Capacitor plugin init, native code). Run:

```
.\scripts\adb-debug.ps1 logs
```

…then launch the app, capture the stack trace, share it. AGP/compileSdk
update is then the next step.

## ISSUE 2 — Tour tooltip disappears when target is large

### Root causes

1. **No explicit max-width on the tooltip JSX.** On narrow viewports a
   long body wraps to many lines and the tooltip's natural width can
   exceed `viewportWidth - margin*2`. `transform: translate(-50%, -50%)`
   centers the box visually but doesn't clamp size.
2. **computeTooltipPosition uses `window.innerHeight`**, which on mobile
   Capacitor INCLUDES the area below the visible viewport on devices with
   3-button nav or notch. The clamp upper bound is below the visually-
   clipped area, so a clamped-to-edge tooltip lands behind the nav.
3. **`isLargeTarget` threshold of 80% missed the 50-79% case.** A
   composer covering 60% of viewport, or a drawer at 50% on landscape,
   still got edge-anchored positioning which placed the tooltip inside
   or behind the highlighted area.

### Fixes shipped

- **`OnboardingTour.tsx` — threshold 80% → 50%.** Catches composers,
  drawers, and other large surfaces. Switches them to centered overlay
  with NO spotlight cutout (just dim background + centered tooltip).
- **`OnboardingTour.tsx` — explicit clamps on tooltip inline style:**
  - `maxWidth: 'min(280px, calc(100vw - 32px))'` — can never overflow
    horizontally regardless of content length
  - `maxHeight: 'calc(100dvh - env(safe-area-inset-top) - env(safe-area-inset-bottom) - 32px)'` — respects safe areas
  - `overflowY: 'auto'` — long body scrolls within the tooltip instead
    of pushing the bottom off-screen

## ISSUE 3 — Memory save error on Android only (works on mobile Chrome)

### Root causes

1. **Auth token cookie jar is separate between Capacitor and Chrome.**
   In mobile Chrome the user is logged in from regular browsing — the
   cookie is present. In Capacitor's WebView the cookie jar starts
   empty and only gets the session via the explicit Auth0 deep-link
   handover flow. If the handover hasn't completed (or expired), the
   POST goes out unauthenticated.
2. **Geolocation permission can be silently denied in Capacitor.** The
   `navigator.geolocation.getCurrentPosition` call fails its second
   callback path; `userCoordinates` stays null; the validation check
   showed a generic message that didn't tell the user it was a permission
   issue.
3. **API responding with HTML (Auth0 challenge or backend 500) makes
   api.post throw a JSON parse error**, which surfaces as a misleading
   error string like "Unexpected token '<'" instead of "your session
   expired".

### Fixes shipped

- **`MapsExperience.tsx` handleCreateMemory** — explicit pre-checks with
  SPECIFIC error copy:
  - `!token` → "Please sign in again — your session has expired."
  - `!userCoordinates` → "Location permission needed. Enable Location
    in Settings → Apps → Brooks."
- **API failure path categorized** by inspecting the thrown error
  message:
  - HTML / JSON-parse → "Your sign-in expired. Tap any tab to reload,
    then sign in again."
  - 401 / 403 / "unauthor" → "Sign-in expired. Reload the app to sign
    in again."
  - network / fetch / "failed to fetch" → "No network connection.
    Check Wi-Fi or mobile data and try again."
  - Otherwise → `Could not save: <actual error>` so user can report it
- **console.error on every save failure** with status + body, captured
  by Chrome DevTools (chrome://inspect/#devices) for diagnosis.

## ISSUE 4 — App icon never shown (multiple AAB rebuilds, same default icon)

This is the most diagnostically tricky one because the AAB has been
verified to contain the correct icons at every density. The "icon never
shows" symptom must come from the install path or launcher rendering.

### Root causes (ranked by likelihood after the FirstPrinciples analysis)

1. **Pixel launcher's themed-icons mode is ON and is suppressing the
   colored icon.** When themed icons are enabled in Wallpaper & Style
   settings on Pixel, the launcher uses ONLY the `<monochrome>` layer
   (a white-on-transparent silhouette) and tints it with the system
   accent color — IGNORING the colored foreground/background. To the
   user, a single-color silhouette of the "B" looks like "default icon".
   The colored icon literally exists in the AAB but the launcher refuses
   to render it because of the user's display preference.
2. **Play Console rolls out internal-track builds asynchronously.**
   Multiple rapid rebuilds in one day — each takes 15-30 min to
   propagate. If the user installs immediately after upload, Play Store
   serves the previously approved version (the OLD broken icon).
3. **Pixel launcher's LauncherDb caches icon objects per-component
   even across uninstall.** The OS-level launcher database keeps icon
   bitmaps; only `pm clear com.google.android.apps.nexuslauncher` or
   a launcher restart guarantees re-extraction.
4. **Legacy Capacitor template files `drawable/ic_launcher_background.xml`
   and `values/ic_launcher_background.xml` existed**, unused by the
   active mipmap-anydpi-v26 XML but potentially confusing AAPT resource
   resolution in edge cases.

### Fixes shipped

- **Removed legacy template files:**
  - `web/android/app/src/main/res/drawable/ic_launcher_background.xml` ← DELETED
  - `web/android/app/src/main/res/values/ic_launcher_background.xml` ← DELETED
- **versionCode bumped 4 → 5** so this build is unambiguously new on
  Play Console; any previous install gets fully replaced.

### MANUAL STEPS YOU MUST DO ON THE PHONE

These are the actual fix for the icon — the code side is already correct.

#### Step 1 — Disable themed icons on Pixel (most likely culprit)

1. Long-press the home screen
2. Tap **Wallpaper & style** (or Settings → Wallpaper & style)
3. Find **Themed icons** toggle
4. **Turn it OFF**
5. Watch the launcher — your colored Brooks icon should appear instantly,
   no reinstall needed.

If the icon appears the moment you toggle themed icons off, that was
the cause for all the prior rebuilds. The colored icon was always there.

#### Step 2 — If themed icons is already off and you still see default

Verify what Play actually delivered:

```
.\scripts\adb-debug.ps1 info
```

Look for `versionCode=5`. If you see 1, 2, 3, or 4 → Play didn't
propagate the latest upload. Wait 30 min and re-check.

#### Step 3 — If versionCode is 5 and icon is still wrong

Force the Pixel launcher to drop its icon cache:

```
adb shell pm clear com.google.android.apps.nexuslauncher
```

The phone's home screen will reset to defaults; your apps reappear with
freshly-extracted icons. The Brooks icon should now be colored.

## Build + upload checklist (one-shot)

From `web/`:

```
node scripts/make-icon-foreground.mjs              # only if source changed
node scripts/add-icon-monochrome.mjs               # only if monochrome regenerated needed
npm run cap:assets                                 # only if icon source changed
node scripts/add-icon-monochrome.mjs               # always re-run after cap:assets (it strips <monochrome>)
cd android
gradlew bundleRelease
```

Upload `android\app\build\outputs\bundle\release\app-release.aab` to
Play Console → Internal Testing. Wait 15-30 min, then on the phone:

1. Uninstall the existing Brooks app
2. Open Play Store via the tester link
3. Install fresh
4. **Turn OFF themed icons** (Pixel settings) if you haven't already
5. Open the app — should NOT crash (error boundary catches any remaining
   first-launch issues)
6. Try saving a memory — should now show specific error if anything
   fails, instead of a generic toast
7. Run the tour — Welcome → Maps → Composer; the tooltip should always
   be readable, never clipped
