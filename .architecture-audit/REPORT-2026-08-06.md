# Brooks Prequel Architecture Intelligence Audit

**Date:** 2026-08-06  
**Issue:** BOR-82 - Deep Architectural Overhaul & Maximum Speed Optimization  
**Scope:** full-system audit, focused remediation, tests, profiling runbook  
**Method:** architecture-intelligence-auditor + systematic debugging

## 1. Executive Summary

Brooks remains correctly shaped as a modular monolith: Java 21/Spring Boot modules behind a Next.js 14 client, PostgreSQL, Docker Compose, Caddy, and a single GCP VM deployment. A microservice split would add failure modes and delivery cost without addressing the measured code risks.

This pass fixed four high-value architectural problems:

1. Guide discovery aggregated three one-to-many tables in one joined rowset, producing multiplicative intermediate rows. Reviews, purchases, and saves are now aggregated independently with PostgreSQL lateral subqueries.
2. AI streams had no enforceable execution budget. They now run for their full lifetime on a bounded named executor and enforce a per-user concurrent-stream limit with HTTP 429 overload behavior.
3. Notification work used an unnamed `@Async` executor. It now uses a separate bounded pool so notification bursts cannot consume AI capacity or create unbounded threads.
4. Simultaneous identical frontend GET requests were sent independently. The API client now coalesces exact token/path matches while in flight and clears coalescing state on mutations.

All backend tests, the application JAR, TypeScript, ESLint, the production Next.js build, and Docker Compose configuration pass. No claim of a percentage speedup is made because a representative production dataset and load trace were not available. The structural improvements are covered by regression tests and a repeatable profiling runbook.

## 2. Application Purpose and Critical Workflows

Brooks is a creator-driven travel marketplace with social discovery, maps, memories, paid guides, purchased trips, reviews, calendar sync, creator earnings, notifications, and optional user-supplied AI providers.

The critical paths are:

- discovery: search/feed/map -> guide or creator profile
- conversion: guide preview -> save or purchase -> payment callback -> versioned access
- trip execution: purchased guide -> itinerary/map/calendar/visited state
- creation: guide editor -> media/place content -> publish
- social: follow/story/review/helpfulness/notification
- memory: create -> visibility/unlock rules -> map rendering
- AI: encrypted user key -> provider stream -> SSE response

Payment, access control, location privacy, user AI keys, and creator payouts are the highest-integrity domains.

## 5. Dependency and Boundary Analysis

Strengths:

- Gradle subprojects make dependencies explicit.
- The composition root fails if an included module directory is absent.
- DTO/service layers exist in core guide, purchase, profile, and memory paths.
- `open-in-view` is disabled, which prevents accidental persistence-session use during serialization.

Residual boundary risks:

- Several modules still import another domain's repositories directly, including AI access to `GuidePurchaseRepository` in `AiChatService.java:11`.
- The shared database has no automated module-ownership rule for tables.
- No ArchUnit test prevents controller-to-repository or cross-module repository dependencies.

Recommendation: add ArchUnit rules before further module growth. Do not split into services until independent scaling, ownership, or deployment cadence provides a concrete reason.

## 6. Data and Query Analysis

### Fixed: guide discovery row multiplication

The old query joined `guide_reviews`, `guide_purchases`, and `saved_guides` directly, then used `COUNT(DISTINCT ...)`. For a guide with R reviews, P purchases, and S saves, the intermediate rowset can approach R x P x S before aggregation.

The new query computes each aggregate independently with `LEFT JOIN LATERAL` at `backend/search/src/main/java/com/brooks/search/repository/SearchRepository.java:153` and again for the catalog path at line 359. Existing indexes on guide/status/time and guide/created-time support these subqueries.

The min-rating count query now uses a correlated aggregate rather than joining all child tables. A SQL-shape regression test prevents raw child joins and `COUNT(DISTINCT ...)` from returning.

### Residual data risks

- SQL is constructed manually; integration tests with PostgreSQL should complement shape tests.
- Query plans must be captured with production-sized cardinalities.
- Ranking and count queries remain separate round trips and could diverge if filters evolve without shared query construction.

## 7. Runtime and Concurrency Analysis

### Fixed: AI stream execution policy

AI streams previously used `CompletableFuture.runAsync`, which supplied no workload isolation or queue limit. The initial provider implementation also scheduled `HttpClient.sendAsync` work and returned before the stream ended.

The corrected design is:

```text
request -> per-user admission permit -> bounded aiTaskExecutor
        -> blocking provider stream on that bounded worker
        -> emitter complete/error/timeout -> idempotent permit release
```

`AsyncExecutionConfig.java:16` defines the AI executor and line 29 defines the notification executor. `AiChatService.java:78` acquires admission and line 85 dispatches bounded work. Provider clients use `HttpClient.send` so the executor and permit cover the complete streaming lifecycle.

Rejected executor submissions and excess per-user streams return HTTP 429. A concurrency regression test at `AiChatServiceConcurrencyTest.java:32` holds a provider stream open and verifies admission remains occupied.

### Fixed: notification isolation

`NotificationService` now uses `@Async("notificationTaskExecutor")`. Its queue is larger and its rejection policy runs overflow on the caller, providing backpressure instead of silently dropping notifications or creating unbounded workers.

## 8. Frontend Runtime Analysis

### Fixed: simultaneous duplicate GETs

The shared API helper now maintains an in-flight map keyed by exact bearer token and path at `web/src/lib/api.ts:13`. Calls at line 23 reuse only an unresolved request. Success and failure both remove the entry, so this is not a stale-data cache.

POST, PUT, PATCH, DELETE, and media upload clear the in-flight map before mutation. This gives safe request coalescing without inventing a broad client cache or changing endpoint response semantics.

### Residual frontend risks

- `MapsExperience.tsx` is 3,239 lines and combines fetching, map lifecycle, filtering, marker DOM, memory state, panels, and responsive UI.
- The map route is the largest listed route bundle at 23.3 kB page code / 139 kB first load.
- No frontend test files were found under `web/src`.
- Production builds log dynamic-server diagnostics from the Auth0 init/logout routes even though the build succeeds.

Recommendation: split map orchestration by responsibility and add Playwright smoke flows before changing map internals.

## 9. Security Analysis

Implemented protection:

- Per-user AI concurrency prevents one authenticated user from monopolizing stream capacity.
- A bounded global AI queue limits memory growth during provider slowness.
- Token identity is part of the frontend GET coalescing key, preventing cross-session response sharing.
- Mutation invalidation prevents an unresolved read from becoming the default response after a write.

Existing strengths:

- Auth0 JWT resource-server enforcement
- explicit public endpoint rules
- encrypted user AI keys
- request IDs without authorization-header logging
- webhook verification and payment status re-fetching

Residual security work:

- Add edge and application rate limits for public search, media, auth proxy, and webhook abuse scenarios.
- Add automated secret scanning and dependency vulnerability checks to CI.
- Perform a dedicated authorization matrix test for owner/buyer/admin endpoints.

- AI stream admission released before asynchronous provider completion.
- AI work escaped the intended bounded executor through `sendAsync`.
- Notification async work did not name an isolated executor.

## 11. Duplication Analysis

Behavioral duplication was found in repeated component-level GET calls, especially shared user/session resources. The API-level coalescer removes transport duplication without requiring every component to coordinate.

No duplicated memory domain implementation was found in this pass. Memory rendering and map integration are separate concerns, but both are concentrated in the same large map component, which can look like duplication because state derivation is repeated around marker and panel lifecycles.

Residual duplication:

- component-level fetch/error/loading patterns are repeated throughout the web app
- SQL filter construction is repeated between guide search and catalog queries
- provider clients repeat HTTP status and stream completion handling

A generic provider abstraction should be introduced only if it preserves provider-specific streaming semantics and error bodies; forced deduplication here could reduce clarity.

## 14. Five Whys: Search Amplification

1. Why did guide search become increasingly expensive? Child rows multiplied before aggregation.
2. Why did rows multiply? Three independent one-to-many tables were joined in one query.
3. Why was `COUNT(DISTINCT)` insufficient? It repaired final counts but did not prevent the large intermediate rowset.
4. Why was the shape accepted? Tests verified mapping behavior but not SQL growth structure.
5. Why was growth structure untested? Representative cardinality and query-plan gates were not part of discovery development.

Root cause: aggregate boundaries were modeled after joins rather than before joins, with no regression assertion for SQL shape.

Correction: independent lateral aggregates plus SQL-shape tests. Follow-up: PostgreSQL integration plan tests with representative data.

## 15. Five Whys: AI Concurrency

1. Why could AI traffic consume uncontrolled resources? Streams were submitted without a named bounded execution policy.
2. Why did adding an executor initially not fully solve it? Providers called `sendAsync` and returned immediately.
3. Why did admission release early? The provider interface returned `void` after scheduling rather than defining completion semantics.
4. Why was that not detected? There was no test holding a stream open and asserting permit occupancy.
5. Why was lifecycle ambiguous? Execution, transport, SSE completion, and admission were implemented in separate layers without one owner for end-to-end lifetime.

Root cause: asynchronous lifecycle semantics were implicit.

Correction: bounded blocking stream workers, explicit per-user permits, idempotent release callbacks, overload status, and an end-to-end concurrency unit test.

## 16. Five Whys: Duplicate Frontend Reads

1. Why were identical API reads repeated? Components independently fetched the same resource.
2. Why did shared layout not eliminate this? Route and feature components also needed the data and had no shared query layer.
3. Why was browser caching insufficient? Authenticated API calls and changing resources were not safely cacheable by default.
4. Why was a full query library not added? It would require application-wide key, invalidation, hydration, and error-state decisions beyond this issue.
5. Why was duplication easy to introduce? The API helper had no transport-level in-flight coordination.

Root cause: fetching was decentralized while transport behavior was stateless.

Correction: exact in-flight GET coalescing with mutation invalidation. Follow-up: adopt a query cache only with explicit resource ownership and invalidation rules.

## 20. Decision Record and Completion Status

Decision: retain the modular monolith and optimize its internal boundaries. Do not introduce microservices, Redis, Kafka, or a frontend cache library solely for BOR-82. The observed problems were query shape, implicit async lifecycle, missing backpressure, and duplicate in-flight transport work; each can be solved locally with lower operational risk.

BOR-82 implementation status: complete for the approved scope.
