## 1. Executive Summary

Brooks is a **modular-monolith Java backend** (Spring Boot 3.3.5 on JDK 21, 11 Gradle modules, Flyway-managed Postgres 16) fronted by a **client-rendered Next.js 14 App Router** frontend, deployed as Docker images to a single GCP VM behind Caddy. The architecture choice (monolith + SPA-style web) is **appropriate for a small team** — the issues are not "wrong shape" but "leaks in the chosen shape."

**Bottom line:** the codebase is healthy in structure and ambitious in product scope, but it has **three concrete production-blocking issues** that need immediate attention, and a layer of **medium-severity hygiene debt** that will compound if not addressed in the next quarter.

**P0 — must fix before next production deploy:**
1. **Real production secrets are committed to git** in `infra/.env.production.example`: Auth0 client secret (line 69), Google OAuth client secret (line 193), AI key encryption secret (line 162). The AI encryption secret is particularly serious — it decrypts every user's stored OpenAI / Anthropic / Gemini keys.
2. **`backend/.dockerignore` missing** — same bug class as the one just fixed in `web/`. Local artifacts get baked into the JVM image and may cause inconsistent builds.
3. **BOG iPay webhook is public** (correct) but the **`Idempotency-Key` is fresh UUID per call** (`BogIpayClient.java:134, 239`) — every retry from the app re-creates the order at BOG, defeating idempotency.

**P1 — within next sprint:** add tests for the money/crypto path (BOG client + AI cipher), split `MapsExperience.tsx` (1807 lines), convert cross-module repository imports to service-level calls.

**P2 — within next quarter:** add frontend tests, scrub env example drift, add AI rate limiting, decide whether `mobile/` ships or gets deleted.

Total findings: **22** (3 critical, 9 high, 7 medium, 3 low). Detailed refactor proposals in §17.

## 2. Application Purpose

Brooks is a **creator-driven travel guide marketplace** — Instagram-style social discovery glued to Google-Maps-style execution, with paid digital products in the middle.

| Actor | Workflow |
|---|---|
| **Creator** | Builds a structured itinerary (Guide → Day → Block → Place), publishes a version, sets price in GEL, can use AI co-pilot (`/api/ai/creator-suggest`) to draft content |
| **Buyer** | Discovers via search/feed/follow → previews title + counts (no itinerary leak) → pays via BOG iPay → access locked to the **exact purchased version**, persisted as a Trip with calendar export |
| **Platform** | 10% fee (configurable), no creator-approval gate, no forking allowed, GEL-only payments, Auth0 SSO |

The "post-purchase" experience (`guide_purchases`, `guide_trip_items`, `TripCalendarEvent`, Google Calendar sync, place visited markers, place reviews) is a distinct domain from the "pre-purchase" social/discovery layer — and the codebase reflects this with the two-table purchase split documented in CLAUDE.md.

## 6. Module Interaction Analysis

### Two-aggregate purchase model
`purchases` (payment record) and `guide_purchases` (trip/access record) are deliberately split, with `PurchaseCompletedEvent` as the in-process bridge. CLAUDE.md documents this clearly. The split is correct.

### SSE streaming flow (AI)
```
Browser → POST /api/ai/creator-suggest (auth: bearer)
   ↓
AiChatController → AiChatService.creatorSuggest()
   ↓ (validates ownership, decrypts user's stored API key)
AiChatService.stream() → CompletableFuture.runAsync()
   ↓
OpenAiClient.streamChat()
   ↓ HttpClient sendAsync, BodyHandlers.ofLines()
   ↓ per line: SseEmitter.send(SseEmitter.event().data(token))
   ↓
Browser EventSource-via-fetch (streamPost in web/src/lib/api.ts)
   ↓ accumulates onToken chunks
CreatorAiPanel.tsx → regex ACTION_PATTERN → pendingAction card
```

**Finding (bug):** `OpenAiClient.streamChat()` (`backend/ai/.../OpenAiClient.java:54-74`) uses `HttpClient.sendAsync(...).thenAccept(...)`. Inside `thenAccept`, `response.body().forEach(...)` can throw a runtime exception that is **silently swallowed by the `try { } catch (Exception ignored) {}` inside the per-line lambda**, and the outer `try` only calls `emitter.complete()` on normal completion. If the OpenAI stream errors mid-flight, the SseEmitter holds open until the 120s timeout in `AiChatService.stream()`. Severity: low (timeout cleans up) but confusing in logs.

### Webhook flow (BOG iPay)
```
BOG → POST /api/webhooks/bog-ipay (public, no Auth0)
   ↓
WebhookController.handleCallback()
   ↓ BogCallbackVerifier.verify(rawBody, signatureHeader)  [RSA SHA256, BOG public key]
   ↓
PurchaseService.handleCheckoutCompleted(orderId)
   ↓ BogIpayClient.getPaymentDetails(orderId)              [defense in depth — re-fetch state]
   ↓ verify status="completed", amount matches, currency=GEL
   ↓
mark COMPLETED (atomic SQL update — idempotent)
   ↓
PurchaseCompletedEvent → GuidePurchaseEventListener
   ↓
GuidePurchaseService.materializeTripForPurchase()
```

This is well designed. The defense-in-depth Payment Details re-fetch is the right call. The atomic update prevents double-grant.

### Hidden coupling
- `OnboardingProvider` (web) calls `api.get('/api/me')` on mount in `AppShell` — every authenticated page eats this call.
- `useAccessToken` cache is module-level (per browser tab process) — race-safe because of `inFlight` dedup, but expiry calc uses `JSON.parse(atob(...))` of JWT payload, which would throw on non-standard tokens (logged as `Date.now() + 50min` fallback). Acceptable.

## 7. Benchmark Architecture Comparison

For a creator-driven marketplace at this team size (~1–3 engineers, single domain, single market), the relevant benchmarks are:

### B1 — Modular Monolith with synchronous in-process events (Brooks's category)
**Examples:** Shopify (pre-Kafka), GitLab, Basecamp, GitHub (circa 2015), early Shopify
**Structure:** One deployable, package/module boundaries enforced by convention or build tool (Gradle sub-projects, Maven modules, .NET projects, Rails engines), shared DB with module-private tables, in-process events.
**Pros:** Single deploy, single trace, fast iteration, refactorable across boundaries; one team can hold the whole thing in their head.
**Cons:** Module boundaries depend on discipline; one slow query blocks the whole app; the temptation to reach across module boundaries grows over time; scaling means scaling the whole.
**Maintenance:** Lowest. Cost: lowest. Adaptability: high while small, decreasing as modules multiply.

### B2 — Domain-driven microservices (the wrong fit at Brooks's size)
**Examples:** Airbnb, DoorDash, Uber
**Structure:** Each bounded context as a separate service with its own DB, event bus (Kafka), service mesh.
**Pros:** Independent deploy/scale per service, fault isolation.
**Cons:** Distributed tracing, transaction sagas, schema evolution across services, on-call hell. Infrastructure cost 5–10× monolith. Requires platform team.
**Not applicable** until Brooks has 10+ engineers and one of these is true: (a) a module needs independent scaling (b) a team needs independent deploy cadence (c) a domain demands different technology.

### B3 — BFF + monolith (the partial fit)
**Examples:** Netflix circa 2014, Shopify Hydrogen
**Structure:** Monolith backend with a thin Backend-for-Frontend layer (Next.js API routes, or a Node BFF) doing aggregation, caching, and shape adaptation for the frontend.
**Pros:** Frontend gets exactly what it needs; backend stays generic; auth concentrated in BFF; can SSR with cached aggregates.
**Cons:** BFF becomes a bottleneck if it owns too much; two codebases to deploy in sync.
**Brooks today:** Next.js is *present* but used as a near-SPA shell — only 2 of 37 pages SSR. The backend pretends a BFF doesn't exist; the frontend talks directly to `/api/*` via Bearer tokens from the browser.

### B4 — JAMstack / Headless commerce
**Examples:** Vercel Commerce, Big Commerce + Next.js
**Structure:** CDN-cached static frontend, all dynamic data via API on the edge, ISR for product pages.
**Pros:** Best LCP, cheapest hosting, SEO-friendly.
**Cons:** Personalization is hard, complex search/filter UX requires hydration.
**Brooks fit:** *partial* — the public guide preview should be JAMstack (and it almost is: `(public)/guides/[id]/page.tsx` uses ISR 60s). The pattern should be extended to creator profile pages and search.

## 10. Bugs Found

### B-1 (HIGH) — BOG iPay Idempotency-Key is random per request
**File:line:** `backend/purchase/src/main/java/com/brooks/purchase/service/BogIpayClient.java:134` (createOrder), `:239` (refund)
**What:** Every call generates `UUID.randomUUID().toString()` as the `Idempotency-Key` header.
**Why it matters:** BOG's API uses this header to dedupe retries. If our app retries `createOrder` (e.g., network blip + Spring's default retry), BOG sees a fresh idempotency key and creates a **second order**. The buyer can be charged twice, or two orders compete for the same external_order_id.
**Fix:** derive from `shopOrderId` for `createOrder` (e.g., `shopOrderId + ":create"`), and for refunds use `orderId + ":refund:" + amount` so the same refund operation is dedup-safe.

### B-2 (MEDIUM) — SSE error path can hang the emitter until timeout
**File:line:** `backend/ai/src/main/java/com/brooks/ai/provider/OpenAiClient.java:54-74`
**What:** `try { } catch (Exception ignored) {}` per-line swallows errors silently. If the JSON parse fails on a non-data line, no error propagates; if the entire stream errors after some tokens, the outer `try/catch` catches it but the inner per-line `catch` may have already obscured the cause.
**Why it matters:** Operators see "AI panel stopped responding for 120s" without a log. Wastes the user's API quota by sending tokens that never reach the browser.
**Fix:** Log at warn level inside the inner catch with the line content; ensure outer `exceptionally(...)` always logs.

### B-3 (MEDIUM) — Module-level token cache survives logout in current tab
**File:line:** `web/src/hooks/useAccessToken.ts:12-14`
**What:** `cachedToken` is a module-level `let`. If a user logs out and back in *within the same tab*, the cached token can be a stale one until the cache expiry fires.
**Why it matters:** After logout, until the cached token expires (up to 50min default), API calls in the same tab will send the old bearer. Backend rejects with 401, so it's not an authz bypass — but it's a confusing UX failure mode.
**Fix:** expose a `clearAccessTokenCache()` export and call it from logout link; or move cache into a React Context that resets on `UserProvider` value change.

### B-4 (LOW) — Stale Docker build for backend (latent, same class as web fix today)
**File:line:** `backend/` (no `.dockerignore`)
**What:** `backend/Dockerfile` `COPY . .` copies local Gradle cache, build artifacts, `.gradle/`, `.idea/`. Some of these (like a stale `app/build/libs/app.jar`) can be overwritten by `./gradlew :app:bootJar`, but the cache layer may use stale checksums.
**Why it matters:** Same class of bug that caused today's incident, just hasn't bitten yet.
**Fix:** add `backend/.dockerignore` excluding `.gradle/`, `**/build/`, `.idea/`, `*.iml`, `.git/`.

### B-5 (LOW) — `cachedTokenExpiresAt` defaults to `Instant.EPOCH`
**File:line:** `backend/purchase/.../BogIpayClient.java:57`
**What:** First request hits the synchronized `ensureToken()`; correct. But if BOG returns a token with no `expires_in`, we cache for 3600s. Aligns with BOG docs but should log when this fallback fires.
**Severity:** Informational.

### B-6 (LOW) — `formatGel(-5)` returns `"0.05"` instead of `"-0.05"`
**File:line:** `backend/purchase/.../BogIpayClient.java:303-307`
**What:** Negative minor units divided by 100 give `whole=0`, but `Math.abs(-5 % 100) = 5`, so formatted as `0.05`. The minus sign is dropped.
**Why it matters:** Only called from `createOrder` and `refund` with positive `long`s today, so latent. But if it ever feeds negative input, you silently send a positive refund amount.
**Fix:** explicit sign: `String sign = minorUnits < 0 ? "-" : ""; long abs = Math.abs(minorUnits); ...`

## 11. Security Issues Found

### S-1 (CRITICAL) — Real production secrets committed in `infra/.env.production.example`
**File:line:**
- `infra/.env.production.example:64` — `AUTH0_SECRET=77b07e9ff2...` (32-byte hex; session cookie encryption)
- `infra/.env.production.example:69` — `AUTH0_CLIENT_SECRET=fHUC1lyT2hk...` (Auth0 application client secret for production app `6eixtLBW...`)
- `infra/.env.production.example:162` — `AI_KEY_ENCRYPTION_SECRET=f34b2f885a3...` (AES-256-GCM key for user AI key encryption at rest)
- `infra/.env.production.example:193` — `GOOGLE_OAUTH_SECRET=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` (Google OAuth client secret)

**Impact:** Anyone with read access to the git repository (including past clones, forks, GitHub viewers, mirrors) holds:
- The ability to forge Auth0 session cookies (`AUTH0_SECRET` is the cookie encryption key in `@auth0/nextjs-auth0`)
- The ability to act as the production Auth0 client (`AUTH0_CLIENT_SECRET` — though the redirect URI is restricted to brooksweb.uk, allowing token exchange only after a real user login)
- The ability to decrypt every stored user AI key in the `user_ai_keys` table given access to a DB dump (`AI_KEY_ENCRYPTION_SECRET`)
- The ability to impersonate the Brooks app to Google Calendar (`GOOGLE_OAUTH_SECRET`)

**Why this matters specifically for `AI_KEY_ENCRYPTION_SECRET`:** the `user_ai_keys` table stores AES-GCM-encrypted OpenAI/Anthropic/Gemini API keys belonging to your *users*. They trusted Brooks with those keys. Compromise means their bills can be run up by anyone with a DB dump and this repo.

**Action required (in order):**
1. **Rotate** all four secrets via their respective vendor consoles.
2. **Re-encrypt** the `user_ai_keys` table: dual-key transition (decrypt with old, re-encrypt with new) in a one-shot script or Flyway repeatable migration.
3. **Scrub** `infra/.env.production.example` to use placeholders (`replace-with-openssl-rand-hex-32`, etc.). The comments at the top of the file already say "This file is documentation" — match the comments.
4. **Purge git history** for these values is **optional but recommended** — `git filter-repo` or `bfg` rewrite. Even after rotation, leaked old values let attackers correlate (e.g., test what other prefixes from this key family were used).
5. **Pre-commit hook** (gitleaks) to prevent recurrence.

### S-2 (HIGH) — No rate limiting on `/api/ai/buyer-chat` and `/api/ai/creator-suggest`
**File:line:** `backend/ai/.../AiChatController.java:29, :35`
**Impact:** Each call streams tokens from OpenAI/Anthropic/Gemini using the *user's* API key (so platform cost is zero), but spends *the user's quota* and consumes a long-lived SseEmitter slot on the server (`120_000ms` timeout each). A single user with a leaked or stolen Brooks session can drain their own AI quota in minutes, or pin server emitter threads.
**Fix:** Bucket4j or Resilience4j RateLimiter at the controller (e.g., 30 messages/min/user). Cap concurrent emitters per user to 1.

### S-3 (MEDIUM) — Webhook endpoint not IP-restricted
**File:line:** `backend/purchase/api/WebhookController.java:54` — `POST /api/webhooks/bog-ipay`, public
**Mitigation in place:** RSA signature verification against a bundled BOG public key (`BogCallbackVerifier`), plus defense-in-depth re-fetch via `getPaymentDetails`.
**Residual risk:** Spam load (anyone can POST garbage and burn CPU on RSA verification). At today's scale, low. At scale, add a Caddy IP allowlist for known BOG IP ranges.
**Note:** signature verification is the right defense; do **not** weaken it.

### S-4 (MEDIUM) — `next dev`-style CSP (unsafe-inline) in production Caddyfile
**File:line:** `infra/Caddyfile.prod` (CSP header line)
**What:** `script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval' *.mapbox.com` allows inline scripts. Mapbox's wasm-unsafe-eval is justified; `unsafe-inline` for scripts is the weak link — it neutralizes XSS protection.
**Fix path:** Switch to nonce-based CSP (`script-src 'self' 'nonce-{nonce}' ...`). Next.js 14 supports it via `headers()` in `next.config.js` + middleware emitting the nonce. Non-trivial but well-documented.

### S-5 (MEDIUM) — Admin authorization relies on email allowlist with no audit trail

## 14. Why Each Change Was Made

- **`web/.dockerignore`** (pre-audit hot-fix): `docker compose build` was copying the host machine's `.next/cache` into the build image. `npm run build` inside the image then re-used that cache and skipped recompilation of `CreatorAiPanel.tsx`. Result: stale bundle shipped, spaces and action-card XML appeared mangled in the browser. The ignore file forces a fresh build inside the image every time.

- **`backend/.dockerignore`** (R2): Backend Dockerfile uses `COPY module/ module/` per module, which copies the host's local `module/build/` and `module/.gradle/` if they exist (left over from local `./gradlew build` or IDE runs). These can override or shadow what the in-image `./gradlew :app:bootJar` produces, causing inconsistent builds. Same bug class as the web fix.

- **`BogIpayClient.java` idempotency key** (R3): BOG iPay deduplicates retries on the `Idempotency-Key` header. The previous code generated `UUID.randomUUID()` per call — a brand new key per retry, so BOG would dedupe nothing. If our app retried `createOrder` (e.g., Spring retry layer, manual user double-click, network blip), BOG would treat each retry as a new order and create a duplicate. Same risk for refunds. Deriving the key from `shopOrderId` (for create) and `orderId + amount` (for refund) makes the key stable across retries, so BOG actually does the dedup.

- **`BogIpayClientTest.java`** (R3 lockdown): The idempotency-key derivation is now load-bearing — if someone changes the format later, BOG silently stops dedup'ing again. The tests pin the exact wire format (`"create:ORDER-123"`, `"refund:ord-1:full"`, `"refund:ord-1:100"`) so a regression breaks the build, not the payment path.

- **`.env.production.example` scrub** (R1): Four real production secrets were committed in plaintext. Scrubbing reduces *future* propagation. Rotation by the user is still required because the secrets are already in git history and any past clone retains them.

- **`.env.example` missing vars** (R11): Five vars consumed in `application.yml` had no entry in the example file, so onboarding a new env required reading YAML to discover them. Adding them with their defaults makes the env contract documented and discoverable.

## 19. Scalability Analysis

**Where will the system first break?**

| Component | First bottleneck | Estimated traffic threshold |
|---|---|---|
| Single Spring Boot instance | Heap (1GB cap in `docker-compose.prod.yml`) under heavy SseEmitter load | ~100 concurrent AI streams |
| Postgres | Lack of read replicas; `guide_purchases` joined with `purchases` on each trip render | ~10k DAU before query plans need attention |
| GCS media reads | Direct user fetch from public bucket; no CDN documented | Whenever | bandwidth becomes a line item |
| Caddy on the same VM as backend | Single point of failure | Whenever single-region SLA matters |
| AI emitter slots | 120s timeout × concurrent users = blocked threads | Tomcat default 200 threads — ~150 concurrent AI streams before queueing |
| `MapsExperience` initial load | 1807-line client bundle | Already large; affects every map view |

**What scales well:**
- Payment path is event-driven (in-process), idempotent at the SQL level — won't double-process.
- Module boundaries (despite leaks) mean a single module can be extracted into a service if/when needed.
- Search uses Postgres full-text — fine until ~100k guides; then move to Meilisearch / Typesense.

**What does not scale well:**
- All AI streaming is on the same Tomcat — needs WebFlux/Netty migration or move AI to its own service for back-pressure.
- Caffeine cache is per-JVM; horizontal scale means stale reads. Either use Redis (already provisioned but unused) or accept the inconsistency.

## 20. Long-Term Architecture Recommendations

**Stay a modular monolith for at least 2 more years.** The architecture is correctly shaped for current team size and product maturity. Microservices would be a mistake. The improvements proposed here are all *within* the monolith pattern.

**Treat the frontend as JAMstack-leaning, not SPA.** The current SPA-style usage of Next.js wastes the framework. The fix is not "rip out Next.js" — it is "use the App Router as designed": server components for public/SEO content, client islands for user-specific interaction. R13 starts this migration.

**Decide on mobile in the next quarter.** The Capacitor footprint suggests a planned native wrap. Either commit (`mobile/` becomes a Capacitor project + CI builds the iOS/Android shells) or remove (drop the `cap:*` scripts and `@capacitor/*` deps, delete `mobile/`). The middle position has costs and benefits zero.

**Plan an AI-as-a-service extraction at ~20× current AI load.** The AI module is the only place where:
- Backpressure matters (each call is a long-lived SseEmitter)
- Cost-amplification risk is real (user API keys can be stolen, drained)
- The product domain is independent enough to extract (no DB writes in the streaming path)

A future split into a small WebFlux service handling only `/api/ai/*` would relieve the monolith's thread pool without disturbing the rest of the architecture.

**Adopt ArchUnit (Java) to enforce module boundaries.** Cheap insurance against the cross-module imports re-appearing after R8.

**Add `gitleaks` to CI.** Today's audit found 4 leaked secrets. The next leak should be caught by a robot, not by Claude on a Sunday afternoon.
