## 1. Executive Summary
Brooks is a travel marketplace/social application implemented as a modular monolith.
Assessment: yellow. Three boundary-lifecycle defects were corrected without changing product contracts:
backup publication, HTTP response consumption, and shared authentication cache invalidation.
Production throughput, recovery readiness and full endpoint authorization remain unverified in this batch.

## 2. Application Purpose
Travelers discover creators and guides, purchase immutable guide versions, plan trips and calendars,
and share location-sensitive memories. CLAUDE.md defines privacy, purchase access and domain boundaries.
Payment confirmation and memory reveal authorization remain backend responsibilities.

## 4. Architecture Map
Browser/native shell -> Next.js -> bearer-authenticated Spring controllers -> domain services -> Postgres.
Backend modules: common, auth, user, profile, social, guide, memory, search, purchase, ai,
notification, community, app. One application deployment, not separately deployed microservices.
The backup sidecar reads Postgres and writes a local named volume.
HTTP lifecycle: web/src/lib/api.ts:118 must finish consuming JSON before releasing cancellation.
Auth lifecycle: web/src/hooks/useAccessToken.ts:45 invalidates all earlier cache writers.
Backup lifecycle: infra/postgres/backup.sh:28 gates publication on dump and compression success.

## 5. Dependency Analysis
Next.js owns presentation and session integration; Spring owns business authorization and persistence.
External network calls introduce latency and failure domains without requiring microservice extraction.
Existing batched memory queries, shared GET promises and bounded AI workers are retained.
No exhaustive dependency-cycle proof or dead-code scan was performed in this follow-up.

## 6. Module Interaction Analysis
JSON GETs are synchronous network operations, coalesced by token/path only while pending.
Caller signals and explicit timeouts now retain independent request ownership.
Token retrieval is shared across mounted consumers; invalidation creates a new ownership generation.
Backup is asynchronous to user requests; failures preserve prior snapshots and retry next interval.
Payment idempotency and purchased-version behavior were not modified or revalidated here.

## 7. Benchmark Architecture Comparison
| Approach | Strength | Cost / limitation | Decision |
| --- | --- | --- | --- |
| Layered monolith | Simple deployment, low operational cost | Domain coupling grows with feature count | Keep layers inside modules, not one undifferentiated service |
| Modular monolith | Explicit domains, local transactions, incremental evolution | Shared runtime and database capacity | Retain; best fit absent evidence of independent scaling needs |
| Microservices | Independent deployment and resource isolation | Distributed consistency, tracing, retries and operational overhead | Defer until measured bottlenecks justify extraction |

Team size and traffic targets were not supplied; no invented capacity thresholds are used.

## 8. Deviation Analysis
Local backups are a deliberate low-cost recovery mechanism, not off-site disaster recovery or PITR.
Reporting a failed dump as successful was an unjustified defect, not an architectural preference.
Early timeout cleanup and unguarded cache writers violate operation ownership; both are corrected.
Independent timeout callers bypass coalescing rather than introducing complex shared cancellation.

## 10. Bugs Found: Five-Step Root Cause Analysis
### B1: Backup failure masked (high)
1. Symptom: an empty or incomplete snapshot can be advertised as successful.
2. Trigger: pg_dump fails while gzip succeeds.
3. Code flaw: POSIX pipeline status only reflects its final command.
4. Architectural gap: publication and retention trusted compression rather than complete production.
5. Correction: independently check dump and compression before rename; prune only after success.
Evidence: infra/postgres/backup.sh:28 and :32. Three command-double regression scenarios cover success,
dump failure and compression failure. Retention and partial cleanup are asserted.

### B2: Response body escapes deadline (high)
1. Symptom: a GET can hang indefinitely after headers, retaining its shared promise.
2. Trigger: a slow/stalled JSON body or cancellation after headers.
3. Code flaw: finally cleared timer/listener before response.json completed.
4. Architectural gap: transport completion was confused with application response completion.
5. Correction: await parsing inside the protected lifecycle, preserve aborts during error parsing.
Evidence: web/src/lib/api.ts:118. Explicit timeout requests do not coalesce (:34).
Regression cases cover timeout cleanup/retry, successful and error-body cancellation and distinct deadlines.

### B3: Logout races with shared token fetch (high)
1. Symptom: old credentials can repopulate the cache after logout.
2. Trigger: an earlier fetch or JSON parse completes after invalidation.
3. Code flaw: unconditional async cache writes and unconditional inFlight cleanup.
4. Architectural gap: shared state lacked ownership across authentication transitions.
5. Correction: generation checks before writes and identity-checked cleanup; hook effects always
consume the current result and ignore unmounted completions.
Evidence: web/src/hooks/useAccessToken.ts:45, :59, :69, :75 and :97.
Tests also cover a token becoming cached between render and effect execution.

## 11. Security Issues
B3 is an authentication-state lifecycle weakness (OWASP A07 category); it is not proof that revoked
tokens bypass backend validation. Existing mounted consumers are not synchronously cleared by this
patch; logout/session architecture still needs an authenticated UI integration test.
No secret scan, penetration test or complete authorization audit was run. Public DTO privacy and
backend JWT issuer/audience validation from prior work were not replaced with client-side checks.

## 14. Change Rationale and Tradeoffs
Backup uses temporary uncompressed SQL to avoid nonportable pipefail assumptions. Peak disk use is
larger and interruption can leave partial files; capacity monitoring remains required. Failure does
not prune previous good backups. Snapshot format stays compatible with existing restore commands.
API keeps default coalescing but sacrifices it for explicitly configured deadlines to preserve caller intent.
Token generation guards avoid a new state library; automatic refresh and subscriber broadcasts are deferred.
Tests use the installed TypeScript compiler, Node test runner and isolated fetch/shell doubles, not new packages.
The report distinguishes local evidence from production verification and unresolved ticket scope.

## 16. Remaining Risks
JVM profiling runbook assumes jcmd/PID 1, but backend/Dockerfile:25 uses a JRE and :37 starts a shell
without exec. The documented profiling command is not a verified diagnostic environment.
Uploads and streaming use separate lifecycles; the JSON deadline fix does not cover them.
Backup volume remains on-VM and uncompressed temporary data increases capacity requirements.
Production build omitted GCS_BUCKET; this does not establish correct production image-host configuration.
React hook mocks verify state transitions but do not replace browser/session integration tests.

## 17. Recommended Improvements
Now: restore drill and off-site recovery design (high, 1-2 days), measured by successful recovery and agreed RPO/RTO.
Next: approved JDK profiling target and representative load test (medium, 1-2 days), measured by p95/p99 and query counts.
Next: streaming/upload/session lifecycle tests (medium, 1-2 days), measured by bounded resource release on cancellation.
Later: isolate workloads only when measurements show shared runtime contention; estimate after profiling.

## 18. Adaptability
Keep new travel, memory and purchase logic in their existing modules and explicit DTO contracts.
Common HTTP/auth primitives offer high leverage but require regression coverage because all routes consume them.
Provider adapters remain appropriate extension points; no new cross-domain dependency was introduced.

## 19. Scalability
Numerical QPS, connection and cost ceilings are unknown without a workload and infrastructure measurements.
This patch bounds stalled JSON network/body lifetimes, not CPU time spent parsing huge synchronous JSON.
Backup peak storage now includes one raw dump plus its compressed output and retained snapshots.
Existing request coalescing and bounded workers remain; no measured throughput improvement is claimed.

## 20. Long-Term Recommendations
Retain the modular monolith, improve observable failure boundaries, then prioritize measured constraints.
Require real restore evidence before claiming disaster recovery and a reproducible workload before speed claims.
Do not close BOR-81/BOR-82 wholesale based on this limited, approved batch.

### Approved Follow-Up: Refund Access and Memory Privacy

The user confirmed that full refunds revoke guide access, and directly shared memories
remain approximate until revealed. These policies are now implemented locally.

- `backend/app/src/main/resources/db/migration/V70__financial_guide_access_sources.sql:1`
  adds financial-purchase provenance and backfills matching historical BOG entitlements.
  Historical fully refunded entitlements without another active payment are canceled.
- `backend/purchase/src/main/java/com/brooks/purchase/service/PurchaseFulfillmentService.java:18`
  rechecks financial status in a fresh transaction under a purchase-row lock. The completion
  listener now belongs to purchase, retaining the existing purchase-to-guide dependency direction.
- `backend/guide/src/main/java/com/brooks/guide/service/GuidePurchaseService.java:247`
  serializes entitlement changes per buyer, links payment sources, reuses canceled trips on
  repurchase, and preserves independent non-BOG access or another active payment source.
- `backend/purchase/src/main/java/com/brooks/purchase/service/PurchaseService.java:412`
  revokes the financial source in the full-refund transaction. Partial refunds retain access.
- `backend/guide/src/main/java/com/brooks/guide/service/GuidePurchaseService.java:583`
  rejects inactive trip reads, edits and calendar exports; restoration checks the same policy.
- `backend/memory/src/main/java/com/brooks/memory/service/MemoryService.java:328`
  quantizes map query bounds as well as locked coordinates. Shared-list responses, geofences,
  failed-reveal distances and public teasers no longer directly expose the exact point or label.
  Owner/revealed content retains exact coordinates. Sensitive location logging was reduced.
- Maps and English/Georgian reveal messages describe distance to the approximate area,
  rather than presenting it as the true distance to the hidden point.
